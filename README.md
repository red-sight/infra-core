# Infra

## About

Infra is a self-assembling infrastructure suite for developing and delivering software-agnostic API microservices. Services declare themselves via Docker labels; Infra detects them, fetches their API documentation, and automatically registers them with the API gateway.

The goal is a zero-configuration quick start — authorization, authentication, routing, caching, and persistence included — targeting MVP projects and beyond.

**Deployment modes:**
- **Local development**: Docker Compose (`docker compose up`)
- **Staging / Production**: Docker Swarm (`docker stack deploy`)

The Registrator handles both modes via an adapter interface. All other components are environment-agnostic.

## Getting Started

**Prerequisites:** Docker with the Compose plugin (Docker Desktop or Docker Engine 24+).

```sh
cp .env.example .env
# edit .env if needed — defaults work for local development out of the box
docker compose up
```

Once all services are healthy, the following URLs are available:

| URL | Service |
|---|---|
| `http://app.localhost` | Frontend (user-configured) |
| `http://app.localhost/api` | API gateway (KrakenD) |
| `http://app.localhost/docs` | Swagger UI |
| `http://auth.app.localhost` | OIDC service (Zitadel) + console at `/ui/console` |
| `http://auth.app.localhost/ui/v2/login` | Zitadel Login UI v2 (separate container) |
| `http://traefik.app.localhost` | Traefik dashboard (dev only) |

> **Note:** `*.localhost` domains resolve to `127.0.0.1` on most systems without any hosts file changes. If they do not resolve in your browser, add them manually to `/etc/hosts`.

## Project Structure

```
docker-compose.yml              # base: images, env vars, networks, volumes, healthchecks
docker-compose.override.yml     # local dev: depends_on, debug ports, Traefik dashboard
docker-compose.swarm.yml        # prod: deploy blocks (replicas, restart policy, placement)
.env.example                    # all env vars with defaults — copy to .env
config/
  krakend/
    krakend.json                # base KrakenD config; endpoints generated by Registrator
scripts/
  postgres/
    init.sh                     # creates per-service databases on first start
  zitadel/
    init.js                     # headless Zitadel bootstrap — runs on every compose up
    zitadel.config.yaml         # declarative config (project, roles, apps, machine users)
registrator/                    # Go service — service discovery, KrakenD config generation
```

### Local development

```sh
cp .env.example .env
docker compose up
```

### Staging / Production (Swarm)

```sh
docker stack deploy -c docker-compose.yml -c docker-compose.swarm.yml infra
```

## Routing

Traefik routes all traffic. Services register themselves via Docker labels — Traefik picks them up automatically with no Registrator involvement.

Default routes:

- `{{ protocol }}://{{ domain }}` — frontend application (e.g. `http://app.localhost`)
- `{{ protocol }}://{{ domain }}/{{ api route }}` — API gateway (e.g. `http://app.localhost/api`)
- `{{ protocol }}://{{ domain }}/docs` — Swagger UI (e.g. `http://app.localhost/docs`)
- `{{ protocol }}://{{ auth subdomain }}.{{ domain }}` — OIDC service / Zitadel (e.g. `http://auth.app.localhost`; console at `/ui/console`, login at `/ui/v2/login`)

Environment variables:

```
INFRA_HTTP_PROTOCOL=http
INFRA_HTTP_BASE_DOMAIN=app.localhost
INFRA_HTTP_OIDC_SUBDOMAIN=auth    # default
INFRA_API_ROUTE=api               # default
```

## Authorization

### RBAC model

Infra uses a flat-roles JWT model. KrakenD validates a single `roles` claim on every protected endpoint — no separate user-role vs org-role distinction at the gateway layer.

**Roles** are Zitadel project roles on the shared "Infra API" project:

| Role | Scope |
|---|---|
| `admin` | Platform-wide |
| `org_owner` | Per-organization (via the org's project grant) |
| `org_user` | Per-organization (via the org's project grant) |

**JWT custom claims** (produced by a Zitadel Action — the "flatten" action — on the Complement Token flow):

- `roles` — flat string array of the user's project roles. KrakenD reads this claim. (The raw Zitadel claim `urn:zitadel:iam:org:project:<id>:roles` is an object; the action flattens it.)
- `organization_id` — the user's organization id.

**Claim propagation to backends:**

| JWT claim | Forwarded header |
|---|---|
| `sub` | `x-user-id` |
| `roles` | `x-user-roles` |
| `organization_id` | `x-organization-id` |

### Scope → role mapping

Services declare required scopes per endpoint via the `x-infra-scopes` OpenAPI extension. The Registrator maps those scopes to the roles that hold them (a gateway authorization policy in its `roles` package — Zitadel project roles carry no scopes — overridable with `INFRA_GATEWAY_ROLE_SCOPES`), then writes the allowed role list into the KrakenD `auth/validator` config. Backend services receive `x-user-roles` and can enforce roles directly.

### Zitadel config

All initial Zitadel configuration is applied by `scripts/zitadel/init.js`, which runs as a one-shot container (`zitadel-init`) on every `docker compose up`. It provisions the instance idempotently via the Management API (using the FirstInstance machine PAT) and writes per-app configs + machine-user credentials to the shared `infra_init_data` volume.

It provisions:
- the shared "Infra API" project + roles (`admin`, `org_owner`, `org_user`) with `projectRoleAssertion`
- OIDC apps (`Admin`, `Tenant`) with `accessTokenRoleAssertion`
- machine users (registrator, service-core) + the Login UI v2 `login-client` (PAT)
- the **flatten Action** (object roles claim → flat `roles` + `organization_id`)
- the platform admin's `admin` role grant

Structural declarations live in `scripts/zitadel/zitadel.config.yaml`. Do not configure Zitadel manually via the console for anything the bootstrap manages — it reconciles on the next `compose up`.

## Registrator

The Registrator is a Go service that connects all components: it watches for healthy candidate services, fetches their OpenAPI documentation, maps scopes to roles via its `roles` policy, and generates and applies KrakenD configuration.

Written in Go for minimal memory and disk footprint — critical for resource-constrained MVP servers.

### Environment Modes

The Registrator auto-detects the environment via the Docker API (`GET /info → .Swarm.LocalNodeState`). Override with `INFRA_MODE=compose|swarm`.

**EnvironmentAdapter interface:**
```go
type EnvironmentAdapter interface {
    WatchServices() <-chan ServiceEvent
    Mode() string
}

type ServiceEvent struct {
    Name    string   // service name — DNS address in both modes
    Port    int
    Healthy bool
    Removed bool
}
```

- **ComposeAdapter**: watches `container` events, filters by `health_status: healthy`
- **SwarmAdapter**: watches `service` task state events, filters by task state `running` with a passing healthcheck

Backend address format is identical in both modes: `http://<service-name>:<port>`. Docker DNS resolves service names on both bridge (Compose) and overlay (Swarm) networks.

### Lazy Reload Policy

To avoid multiple KrakenD restarts when several services become healthy simultaneously, the Registrator applies a debounce before reloading:

```
INFRA_REGISTRATOR_RELOAD_DELAY=5s    # local development default
INFRA_REGISTRATOR_RELOAD_DELAY=60s   # staging/production default
```

On each new healthy `ServiceEvent`, the debounce timer resets. When it fires, the Registrator generates a new KrakenD config and restarts the KrakenD container.

### Service Declaration

A candidate service must exist on the same Docker network and declare itself via labels:

| Label | Required | Default | Description |
|---|---|---|---|
| `infra.enabled` | yes | — | must be `true` to be discovered |
| `infra.name` | yes | — | service identifier, used in gateway routes |
| `infra.port` | yes | — | internal container port the service listens on |
| `infra.openapi-route` | no | `openapi` | path where the OpenAPI spec is served |
| `infra.auth.protected` | no | `true` | default auth requirement for all endpoints |

The service must also provide a Docker healthcheck.

### OpenAPI Extension Labels

Declared per-operation in the service's OpenAPI spec:

| Extension | Default | Description |
|---|---|---|
| `x-infra-protected` | inherits `infra.auth.protected` | `false` = public endpoint, no `auth/validator` block generated |
| `x-infra-scopes` | `[]` | required scopes; Registrator resolves these to roles via its `roles` policy |
| `x-infra-scopes-matcher` | `"any"` | `"any"` (OR) — at least one listed scope; `"all"` (AND) — every scope required |

### Registration Flow

1. A healthy `ServiceEvent` is received
2. Debounce timer starts (or resets)
3. When the timer fires:
   - Fetch OpenAPI spec from `http://<service-name>:<port>/<openapi-route>`
   - Build the scope→role map from the `roles` policy
   - Parse endpoints and their `x-infra-*` extensions
   - Generate KrakenD endpoint configs, including `auth/validator` blocks for protected endpoints
   - Write new KrakenD config and restart KrakenD

## Services

### Traefik

Image: `traefik:v3.7`

Reverse proxy and service discovery. Configured via Docker labels on each service. The `docker-compose.override.yml` enables the insecure dashboard for local development, accessible at `http://traefik.app.localhost`.

### Zitadel

Image: `ghcr.io/zitadel/zitadel:v4.15.2`

OIDC identity provider (one instance, one issuer, RS256; per-organization isolation). Depends on Postgres. Listens on `:8080` (gRPC + REST + console), routed via `auth.{{ domain }}`. The hosted login UI is a **separate container** (`zitadel-login`) routed at `auth.{{ domain }}/ui/v2/login`; a one-shot `zitadel-prepare` makes the machinekey volume writable for Zitadel's non-root user.

### Zitadel Login UI v2

Image: built from [`zitadel-login/`](zitadel-login/) (`INFRA_ZITADEL_LOGIN_IMAGE`)

Login v2 is a separate Next.js app in Zitadel v4, so it is the one piece of the auth surface whose appearance we can own. We run a **fork of upstream `apps/login`** (vendored at tag `v4.15.2`), re-skinned to the admin console's font and radii — the login flow itself is upstream's, unmodified.

The **colors** come from Zitadel's label policy (private labeling), which overrides anything compiled into the login. The platform palette is the `branding:` block in `scripts/zitadel/zitadel.config.yaml`, applied on every bootstrap by `zitadel-init`; edit it there, not in the fork. An organization that sets its own label policy overrides it, which is how per-org branding works.

Setting `INFRA_ZITADEL_LOGIN_IMAGE=ghcr.io/zitadel/zitadel-login:v4.15.2` reverts to the stock upstream image — the runtime contract is identical. See [`zitadel-login/README.md`](zitadel-login/README.md) for the build, the exact list of changes, and the upstream re-sync procedure.

OIDC endpoints (auto-derived from env vars):

```
Discovery: {{ protocol }}://{{ oidc subdomain }}.{{ domain }}/.well-known/openid-configuration
JWKS:      {{ protocol }}://{{ oidc subdomain }}.{{ domain }}/oauth/v2/keys
Issuer:    {{ protocol }}://{{ oidc subdomain }}.{{ domain }}
```

### zitadel-init

Image: `node:22-alpine` (one-shot init container)

Runs `scripts/zitadel/init.js` on every `docker compose up` (`restart: on-failure`). Provisions the instance idempotently via the Management API and writes machine-user credentials + per-app configs to the `infra_init_data` shared volume.

Environment variables (set on the `zitadel` service / passed through):

```
INFRA_ZITADEL_MASTERKEY=             # required — exactly 32 chars
INFRA_ZITADEL_ADMIN_USERNAME=admin   # default — console admin
INFRA_ZITADEL_ADMIN_PASSWORD=        # required — must meet Zitadel complexity
INFRA_PG_ZITADEL_DB=zitadel          # default
INFRA_DEFAULT_ORG_NAME=              # default org (apex / non-SaaS case)
```

### KrakenD

Image: `krakend:latest`

API gateway. Configuration is fully generated by the Registrator — no manual JSON editing required. Base config lives in `config/krakend/krakend.json` with an empty endpoints array; the Registrator writes and reloads this file.

KrakenD validates JWTs per endpoint using the `auth/validator` extra config block. It does not support OIDC auto-discovery — the JWKS URL must be provided explicitly.

Generated config per protected endpoint:

```json
{
  "extra_config": {
    "auth/validator": {
      "alg": "RS256",
      "jwk_url": "{{ protocol }}://{{ oidc subdomain }}.{{ domain }}/oauth/v2/keys",
      "audience": ["<Zitadel project id>"],
      "roles": ["<resolved from x-infra-scopes via the roles policy>"],
      "roles_key": "roles",
      "propagate_claims": [
        ["sub", "x-user-id"],
        ["roles", "x-user-roles"],
        ["organization_id", "x-organization-id"]
      ],
      "cache": true,
      "cache_duration": 900,
      "disable_jwk_security": true
    }
  }
}
```

`disable_jwk_security` must be `true` when Zitadel is served over HTTP (local development). Set to `false` for staging and production.

### Swagger UI

Serves the aggregated OpenAPI spec at `http://app.localhost/docs`. The spec is fetched dynamically at page load via `SWAGGER_JSON_URL`, which points to the Registrator's `/openapi.json` endpoint (`http://${INFRA_HTTP_BASE_DOMAIN}/openapi.json`). No container restart is required when the spec updates — a browser refresh is sufficient.

### Redis

Image: `redis:7-alpine`

Shared caching and queuing for infra microservices. Services must use a key prefix scoped to their service name:

```
<service-name>:<key>
```

Example: `my-service:session:abc123`

### NATS

Image: `nats:2.10-alpine`

Message bus with JetStream enabled. Used for async events and job queues between microservices. JetStream provides at-least-once delivery and persistent streams. Management port: `8222`.

### service-core

Image: built from repo root (Go, uses `go.work`)

Core platform service. Stack: Huma v2 + Chi router, GORM, goose migrations (embedded SQL files), Postgres. Module: `infra/service-core`, database: `service_core`.

Current endpoints:

| Method | Path | Required scope |
|---|---|---|
| `GET` | `/admin/organizations` | `read:organizations` |
| `POST` | `/admin/organizations` | `write:organizations` |
| `GET` | `/tenant/by-host?host=` | public (no auth) |

Scopes declared: `read:organizations`, `write:organizations`, `delete:organizations` — assigned to the `admin` role. `GET /tenant/by-host` is public: the tenant frontend calls it (before login) to resolve its organization (and its Zitadel `external_id`, used to scope login) from its hostname.

Each organization has a DNS-safe `slug` (validated, reserved-word-checked) that addresses its tenant frontend at `<slug>.<base-domain>`. On create, the outbox worker also grants the org the shared Infra API project and appends `<slug>`'s callback URL to the shared Zitadel `Tenant` app so that subdomain can authenticate.

**Master organization.** The org with an **empty slug** is the master org (product owner's), served on the apex domain `<base-domain>` instead of a subdomain. `UNIQUE(slug)` allows at most one; service-core seeds it on startup (`INFRA_DEFAULT_ORG_NAME`) and provisions it in Zitadel with the apex callback. It is created by initialization, not via the admin form.

**Organizations: core is the source of truth, Zitadel is a follower.** `POST /admin/organizations` writes the organization row and a `outbox_events` row in one DB transaction, then returns `201` with `synced: false`. A background outbox worker provisions the organization in Zitadel (via the `service-core` machine user), fills the provider-neutral `external_id`, and the organization reports `synced: true`. Delivery retries with backoff and is idempotent (by Zitadel's unique org name) — there is no periodic reconciliation. service-core reads its M2M creds from `/run/infra/service-core-m2m.json` (`INFRA_SERVICE_CORE_M2M_FILE`); outbox tuning via `OUTBOX_POLL_INTERVAL`, `OUTBOX_MAX_ATTEMPTS`.

Uses the shared `infra/query` module (`github.com/red-sight/infra-core/query`) for pagination, sort, search, date range, and field filters.

### Postgres

Image: `postgres:17-alpine`

Each service requiring database access receives its own database. On first start, `scripts/postgres/init.sh` creates all required databases. In Swarm, the Postgres container is pinned to a specific node via `node.labels.infra.postgres == true` to ensure data volume persistence.

Default environment variables:

```
INFRA_PG_USER=postgres
INFRA_PG_PASSWORD=postgres
INFRA_PG_ZITADEL_DB=zitadel
INFRA_PG_CORE_DB=service_core
```
