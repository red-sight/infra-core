# zitadel-login — forked Login UI v2

Our fork of ZITADEL's Login UI v2 (`apps/login` from
[zitadel/zitadel](https://github.com/zitadel/zitadel)), re-skinned to the admin
console's design language. Zitadel's login flow and its security surface are
untouched — the diff is design tokens, not behaviour.

Vendored from tag **`v4.15.2`**, which must match the `ghcr.io/zitadel/zitadel`
image in [docker-compose.yml](../docker-compose.yml).

## Why a fork

Login v2 is a separate Next.js app in ZITADEL v4, not part of the core image, so
the only way to control its appearance beyond per-org colors and logo (which
Zitadel's private labeling already covers) is to run our own build of it. The
admin console is Vue + radix-vue and the login is React/Next — no component is
shared, so parity comes from porting token *values*, not code.

## Layout

```
zitadel-login/
├── apps/login/          our fork of upstream apps/login
├── packages/
│   ├── zitadel-client/  upstream package, verbatim (built with tsup)
│   └── zitadel-proto/   upstream package, verbatim (generated by buf)
├── proto/               ZITADEL's protos, verbatim from the tag
├── proto-deps/          FORK: vendored third-party protos (see its README)
├── buf.yaml             FORK: buf v2 workspace replacing proto/buf.yaml
└── Dockerfile           FORK: self-contained multi-stage build
```

This mirrors upstream's monorepo layout on purpose: `apps/login/package.json`
keeps its `workspace:*` dependencies and its standalone build script unchanged,
so re-syncing is a file copy rather than a re-patch.

The npm-published `@zitadel/client` / `@zitadel/proto` are **not** usable — they
were last published (1.3.1) from the archived `zitadel/typescript` repo and are a
year behind the v4 login sources (missing `Code`, `ConnectError`, `verifyJwt`, …).
Both are built from the pinned tag instead.

## Build and run

```bash
pnpm install
pnpm build            # proto codegen -> @zitadel/client -> next build (standalone)
pnpm test             # upstream's vitest suite
pnpm lint
pnpm dev              # local dev server, needs a reachable ZITADEL
```

In the stack it is built and run by Compose like any other service:

```bash
docker compose up -d --build zitadel-login
```

`INFRA_ZITADEL_LOGIN_IMAGE` selects the image (default `zitadel-login:latest`).
Setting it to `ghcr.io/zitadel/zitadel-login:v4.15.2` runs the stock upstream
login instead — the runtime contract (`ZITADEL_API_URL`,
`ZITADEL_SERVICE_USER_TOKEN_FILE`, port 3000, `/ui/v2/login` base path) is
identical, so that fallback is always available. Swarm ignores `build`, so CI
must push the image and set the variable.

Proto codegen is hermetic (no Buf Schema Registry at build time); the only
build-time network dependencies are the npm registry and, for `next/font`,
fonts.googleapis.com.

## What we changed

Kept deliberately small so upstream diffs stay reviewable. Every change is marked
with a `FORK:` comment.

| File | Change |
|---|---|
| `apps/login/src/helpers/colors.ts` | Fallback branding colors → admin's zinc palette / near-black primary (mirrors the bootstrap's `branding:` block) |
| `apps/login/src/app/(login)/layout.tsx` | Lato → Geist (admin's `--font-sans`); footer controls kept aligned to the card |
| `apps/login/tailwind.config.mjs` | `borderRadius` scale → admin's `--radius*` (cards 10px, controls 8px) |
| `apps/login/src/styles/globals.scss` | `--ui-*` chrome tokens (border/ring/muted/accent/shadow), base type size, heading scale, smoothing, scrollbars, selection |
| `apps/login/src/components/input.tsx` | admin's `.field` + `.input` — 36px control, hairline border, admin focus ring, 13px medium label |
| `apps/login/src/components/button.tsx` | admin's `.btn` metrics (13.5px/500, 36px, focus ring) and `.btn--outline` secondary |
| `apps/login/src/components/dynamic-theme.tsx` | 24px card rhythm; brand lockup fallback; full-height card on phones; dropped an empty trailing div |
| `apps/login/src/components/theme-wrapper.tsx` | passes the shell's height through, so the mobile full-height chain isn't broken |
| `apps/login/src/components/brand-logo.tsx` | **New** — platform brand lockup (admin's layers mark + wordmark), used when an org has no `logoUrl` |
| `apps/login/src/components/alert.tsx` | admin's `--warn-*` / neutral surfaces instead of raw Tailwind yellow |
| `apps/login/src/components/theme-switch.tsx` | admin's segmented-control chrome |
| `apps/login/src/lib/theme.ts` | `flat` appearance → admin card chrome; `regular` padding → admin's 24px |
| `apps/login/.env` | Pinned theme layout/appearance/spacing |
| `apps/login/package.json` | Dropped devDeps that only served the removed acceptance/dockerized suites |
| `buf.yaml`, `proto-deps/` | Hermetic proto codegen (replaces `proto/buf.yaml`) |
| `Dockerfile` | Builds from source instead of packaging a host-built bundle |
| removed | `acceptance/`, `dockerized/`, `screenshots/`, `project.json` (nx), `vercel.json` |

**Colors do not come from this fork at runtime.** Zitadel's label policy (private
labeling) wins over the compiled-in defaults whenever a field is set, and the stock
instance policy ships Zitadel blue — so the palette that actually reaches the screen
is the `branding:` block in
[scripts/zitadel/zitadel.config.yaml](../scripts/zitadel/zitadel.config.yaml),
applied by `zitadel-init`. The constants in `helpers/colors.ts` mirror it and are
the fallback for an organization whose policy is unset. **Change both together.**
This is also what keeps per-org branding working: an org that sets its own label
policy overrides the platform palette, exactly as upstream intends.

**The logo follows the same rule with one exception.** An organization's uploaded
`logoUrl` (label policy) always wins. When there is none, the login renders the
built-in `BrandLogo` — admin's layers mark plus the `NEXT_PUBLIC_BRAND_NAME`
wordmark. It is a component rather than an uploaded asset so it tracks the branded
primary color and both themes without maintaining two image files; the trade-off is
that it does not appear in the Zitadel console. Upload a real logo to the instance
label policy if you want one identity in both places.

The design target is `admin/src/assets/theme.css`. Parity is visual, not
structural — we replicate palette, font and radii, not admin's components, and
the two are not kept in lockstep.

## Re-syncing an upstream release

1. Check out the new ZITADEL tag and copy `apps/login`, `packages/zitadel-client`,
   `packages/zitadel-proto` and `proto/` over the vendored copies (drop
   `acceptance/`, `dockerized/`, `screenshots/`, `project.json`, `vercel.json`
   again, and delete `proto/buf.yaml` + `proto/buf.lock` — our root `buf.yaml`
   replaces them).
2. Re-apply the `FORK:` changes in the table above (`git diff` against the
   previous vendored tree shows them).
3. Diff the new `proto/buf.lock` against `proto-deps/README.md` and re-vendor the
   dependency protos if the pinned commits moved.
4. Mirror upstream's root `pnpm-workspace.yaml` `overrides` block.
5. `pnpm install && pnpm build && pnpm test`, then bump the tag in this README,
   the image table in `AGENTS.md`, and the upstream fallback tag in
   `docker-compose.yml`.
